# 사용자 스토리 (User Stories)

## 1. 대기열 시스템

### US-001: 대기열 토큰 발급
**As a** 콘서트 예약을 원하는 사용자,
**I want** 대기열에 참여하여 고유한 토큰을 발급받고,
**So that** 공정한 순서대로 좌석 예약 기회를 얻을 수 있다.

**Acceptance Criteria:**
- [ ] 사용자가 대기열 토큰 발급 API를 호출하면 UUID 기반의 고유한 토큰이 생성된다
- [ ] 토큰은 각 사용자당 하나만 발급되며, 중복 발급되지 않는다
- [ ] 현재 입장되어 있는(ACTIVE) 사용자가 500명 미만이고 대기열이 비어있으면 즉시 ACTIVE 상태 토큰을 발급받는다
- [ ] 현재 입장된 인원이 500명 이상이거나 대기열에 대기자가 있으면 WAITING 상태 토큰을 발급받는다
- [ ] 토큰 발급 시 대기 순번과 예상 대기 시간 정보가 함께 반환된다
- [ ] WAITING 상태 토큰은 만료 시간이 없으며 무한 대기 가능하다
- [ ] ACTIVE 상태로 전환된 토큰은 30분의 만료 시간이 설정된다

---

### US-002: 대기 순서 조회
**As a** 대기 중인 사용자,
**I want** 내 현재 대기 순번과 상태를 조회하고,
**So that** 언제 좌석 예약을 시작할 수 있는지 알 수 있다.

**Acceptance Criteria:**
- [ ] 유효한 토큰으로 대기 순서 조회 API를 호출할 수 있다
- [ ] 응답에는 현재 대기 순번, 대기 상태(WAITING/ACTIVE), 남은 대기 인원이 포함된다
- [ ] 토큰이 만료되었거나 유효하지 않으면 `TOKEN_EXPIRED` 또는 `TOKEN_INVALID` 에러가 반환된다
- [ ] 대기 순서 조회는 100ms 이내에 응답되어야 한다
- [ ] WAITING 상태 토큰은 만료 시간 없이 대기 순번만 표시된다
- [ ] ACTIVE 상태 토큰의 경우 남은 유효 시간(최대 30분)이 표시된다

---

### US-003: 자동 대기열 입장 처리
**As a** 시스템,
**I want** 10초마다 대기열에서 10명씩 자동으로 입장시키고,
**So that** 대기 중인 사용자들이 순차적으로 좌석 예약 기회를 얻을 수 있다.

**Acceptance Criteria:**
- [ ] 스케줄러가 10초마다 자동으로 실행된다
- [ ] 현재 입장되어 있는(ACTIVE 상태) 사용자 수가 500명 이하일 때만 입장 처리가 진행된다
- [ ] 입장된 인원이 500명 초과이면 스케줄러는 대기열 처리를 건너뛰고 다음 주기까지 대기한다
- [ ] 대기열에서 가장 앞에 있는 10명의 토큰 상태가 WAITING에서 ACTIVE로 변경된다
- [ ] ACTIVE 상태로 변경된 토큰의 만료 시간이 30분으로 설정된다
- [ ] 대기열이 10명 미만이면 남은 인원만큼만 입장 처리된다

---

### US-004: 토큰 만료 처리
**As a** 시스템,
**I want** 만료 시간이 지난 토큰을 자동으로 정리하고,
**So that** 시스템 리소스를 효율적으로 관리하고 다음 대기자에게 기회를 제공할 수 있다.

**Acceptance Criteria:**
- [ ] WAITING 상태 토큰은 만료되지 않으며 무한 대기 가능하다
- [ ] ACTIVE 상태 토큰은 활성화 시점으로부터 30분이 지나면 자동 만료된다
- [ ] 만료된 ACTIVE 토큰으로 API 요청 시 `TOKEN_EXPIRED` 에러가 반환된다
- [ ] Redis TTL을 활용하여 ACTIVE 토큰의 만료 시간을 자동 관리한다
- [ ] ACTIVE 토큰 만료 시 해당 사용자의 임시 예약 좌석이 있다면 함께 해제된다
- [ ] ACTIVE 토큰이 만료되면 입장된 인원 수가 감소하여 새로운 대기자 입장 기회가 생긴다

---

## 2. 좌석 예약 시스템

### US-005: 예약 가능한 좌석 목록 조회
**As a** 입장이 완료된(ACTIVE) 사용자,
**I want** 예약 가능한 좌석 목록을 조회하고,
**So that** 원하는 좌석을 선택하여 예약할 수 있다.

**Acceptance Criteria:**
- [ ] 유효한 ACTIVE 상태의 토큰을 헤더에 포함하여 API를 호출할 수 있다
- [ ] WAITING 상태 또는 만료된 토큰으로 요청 시 에러가 반환된다
- [ ] 응답에는 좌석 ID, 좌석 번호, 가격, 상태(AVAILABLE/TEMP_RESERVED/CONFIRMED)가 포함된다
- [ ] AVAILABLE 상태의 좌석만 예약 가능하다는 것이 명확히 표시된다
- [ ] 좌석 목록 조회는 200ms 이내에 응답되어야 한다

---

### US-006: 좌석 임시 예약
**As a** 입장이 완료된 사용자,
**I want** 원하는 좌석을 임시로 예약하고,
**So that** 5분 동안 해당 좌석을 점유하고 결제를 진행할 수 있다.

**Acceptance Criteria:**
- [ ] 유효한 ACTIVE 토큰과 좌석 ID로 임시 예약 API를 호출할 수 있다
- [ ] AVAILABLE 상태의 좌석만 예약 가능하며, 그 외 상태는 `SEAT_NOT_AVAILABLE` 에러가 반환된다
- [ ] 좌석 상태가 AVAILABLE에서 TEMP_RESERVED로 변경된다
- [ ] 임시 예약된 좌석에는 예약자 정보와 예약 만료 시간(5분 후)이 기록된다
- [ ] 동시에 여러 사용자가 같은 좌석을 예약하려 할 때 한 명만 성공한다 (동시성 제어)
- [ ] 한 사용자가 이미 임시 예약한 좌석이 있으면 추가 예약이 불가능하다
- [ ] 좌석 예약 처리는 200ms 이내에 완료되어야 한다

---

### US-007: 임시 예약 자동 만료
**As a** 시스템,
**I want** 5분 내에 결제되지 않은 임시 예약 좌석을 자동으로 해제하고,
**So that** 다른 사용자가 해당 좌석을 예약할 수 있도록 한다.

**Acceptance Criteria:**
- [ ] 스케줄러가 주기적으로 임시 예약 만료 시간을 확인한다
- [ ] 임시 예약 후 5분이 경과한 TEMP_RESERVED 좌석이 AVAILABLE로 복원된다
- [ ] 좌석 복원 시 예약자 정보가 삭제된다
- [ ] 만료된 임시 예약 건으로 결제 시도 시 `TEMP_RESERVATION_EXPIRED` 에러가 반환된다

---

## 3. 결제 시스템

### US-008: 포인트를 사용한 결제
**As a** 임시 예약을 완료한 사용자,
**I want** 보유한 포인트와 현금을 사용하여 결제하고,
**So that** 좌석 예약을 확정하고 할인 혜택을 받을 수 있다.

**Acceptance Criteria:**
- [ ] 유효한 ACTIVE 토큰과 결제 정보(포인트 사용 플래그)로 결제 API를 호출할 수 있다
- [ ] 포인트 사용 플래그가 true일 경우, 보유 포인트를 먼저 차감하고 남은 금액을 현금에서 차감한다
- [ ] 포인트 사용 플래그가 false일 경우, 전액 현금으로 결제한다
- [ ] 포인트 사용 시 총 잔액(포인트 + 현금)이 부족하면 `INSUFFICIENT_BALANCE` 에러가 반환된다
- [ ] 포인트 미사용 시 현금이 부족하면 `INSUFFICIENT_BALANCE` 에러가 반환된다
- [ ] 결제 성공 시 좌석 상태가 TEMP_RESERVED에서 CONFIRMED로 변경된다
- [ ] 결제 성공 시 대기열 토큰이 만료 처리된다
- [ ] 결제 내역이 데이터베이스에 저장된다
- [ ] 결제 처리는 500ms 이내에 완료되어야 한다

---

### US-009: 현금만 사용한 결제
**As a** 포인트를 사용하지 않으려는 사용자,
**I want** 전액 현금으로 결제하고,
**So that** 포인트를 나중에 사용할 수 있도록 저축할 수 있다.

**Acceptance Criteria:**
- [ ] 포인트 사용 플래그를 false로 설정하여 결제 API를 호출할 수 있다
- [ ] 결제 금액만큼 현금만 차감되고 포인트는 차감되지 않는다
- [ ] 현금 잔액이 부족하면 `INSUFFICIENT_BALANCE` 에러가 반환된다
- [ ] 결제 성공 시 현금 사용 금액의 5%가 포인트로 적립된다
- [ ] 좌석 상태가 CONFIRMED로 변경되고 토큰이 만료된다

---

### US-010: 포인트 적립
**As a** 결제를 완료한 사용자,
**I want** 현금 결제 금액의 5%를 포인트로 적립받고,
**So that** 다음 예약 시 포인트를 사용하여 할인받을 수 있다.

**Acceptance Criteria:**
- [ ] 결제 완료 즉시 포인트가 자동으로 적립된다
- [ ] 현금으로 결제한 금액에 대해서만 5%가 적립된다 (포인트 사용분 제외)
- [ ] 적립 계산식: (현금 사용 금액) × 5%
- [ ] 적립된 포인트가 사용자의 포인트 잔액에 즉시 반영된다
- [ ] 포인트 적립 내역이 결제 내역과 함께 저장된다

---

### US-011: 결제 실패 시 좌석 복원
**As a** 시스템,
**I want** 결제 실패 시 임시 예약된 좌석을 그대로 유지하고,
**So that** 사용자가 잔액을 충전한 후 다시 결제를 시도할 수 있다.

**Acceptance Criteria:**
- [ ] 결제 실패 시 좌석 상태는 TEMP_RESERVED 상태로 유지된다
- [ ] 임시 예약 만료 시간(5분)은 그대로 유지된다
- [ ] 사용자에게 실패 원인(잔액 부족 등)이 명확히 전달된다
- [ ] 사용자는 만료 시간 내에 다시 결제를 시도할 수 있다

---

## 4. 사용자 및 지갑 관리

### US-012: 사용자 등록
**As a** 신규 사용자,
**I want** 계정을 생성하고 기본 정보를 입력하고,
**So that** 콘서트 예약 서비스를 이용할 수 있다.

**Acceptance Criteria:**
- [ ] 사용자 ID, 이름, 이메일을 입력하여 계정을 생성할 수 있다
- [ ] 계정 생성 시 빈 지갑(Wallet)이 자동으로 생성된다
- [ ] 지갑의 초기 현금과 포인트는 0원으로 설정된다
- [ ] 중복된 사용자 ID 또는 이메일로 가입 시 에러가 반환된다
- [ ] 생성 시간(createdAt)이 자동으로 기록된다

---

### US-013: 잔액 충전
**As a** 등록된 사용자,
**I want** 지갑에 현금을 충전하고,
**So that** 좌석 예약 결제에 사용할 수 있다.

**Acceptance Criteria:**
- [ ] 사용자 ID와 충전 금액을 입력하여 충전 API를 호출할 수 있다
- [ ] 충전 금액이 현금 잔액에 즉시 반영된다
- [ ] 충전 내역이 결제 내역에 기록된다
- [ ] 충전 금액은 양수여야 하며, 0 또는 음수는 거부된다
- [ ] 지갑의 updateAt 필드가 자동으로 갱신된다

---

### US-014: 잔액 조회
**As a** 사용자,
**I want** 내 현재 현금 및 포인트 잔액을 조회하고,
**So that** 결제 가능 여부를 확인할 수 있다.

**Acceptance Criteria:**
- [ ] 사용자 ID로 지갑 조회 API를 호출할 수 있다
- [ ] 응답에는 현재 현금 잔액, 포인트 잔액, 마지막 업데이트 시간이 포함된다
- [ ] 존재하지 않는 사용자 ID로 조회 시 `NOT_EXIST_USER` 에러가 반환된다
- [ ] 지갑이 없는 사용자는 `SERVER_ERROR` 에러가 반환된다

---

## 5. 비기능 요구사항

### US-015: 동시성 제어
**As a** 시스템,
**I want** 여러 사용자가 동시에 같은 좌석을 예약하려 할 때 한 명만 성공하도록 제어하고,
**So that** 데이터 무결성을 보장하고 이중 예약을 방지할 수 있다.

**Acceptance Criteria:**
- [ ] 좌석 예약 시 낙관적 락 또는 비관적 락을 사용하여 동시성을 제어한다
- [ ] 동시에 같은 좌석 예약 요청이 들어오면 한 명만 성공하고 나머지는 `SEAT_NOT_AVAILABLE` 에러가 반환된다
- [ ] 트랜잭션 격리 레벨을 적절히 설정하여 잔액 차감 시 동시성 문제를 방지한다
- [ ] 동시 요청 테스트를 통해 데이터 무결성이 보장됨을 검증한다

---

### US-016: 성능 요구사항 충족
**As a** 시스템,
**I want** 모든 API 요청이 정해진 시간 내에 응답되고,
**So that** 사용자에게 원활한 예약 경험을 제공할 수 있다.

**Acceptance Criteria:**
- [ ] 대기열 순번 조회는 100ms 이내에 응답된다
- [ ] 좌석 예약 처리는 200ms 이내에 완료된다
- [ ] 결제 처리는 500ms 이내에 완료된다
- [ ] 성능 테스트를 통해 동시 사용자 1000명 이상 처리 가능함을 검증한다
- [ ] Redis를 활용하여 대기열 및 토큰 조회 성능을 최적화한다
